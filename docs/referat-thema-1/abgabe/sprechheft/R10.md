## Verstehen

Reservefolie für die Frage nach 1B Schritt 1: Wie wurde das Zwei-Host-Deployment nachgebaut, und wo weicht es von ADR-0035 ab? Der Auftrag verlangt ausdrücklich, App-Adapter, Encoder und LLM-Server zu unterscheiden.

**Aufbau der Folie.** Oben drei Kästen nebeneinander:

- **App-Adapter, app-host:** `openWeightLlmClient.ts` ruft die Runtime mit Bearer-Token; Gate und Fallback in `qaSummaryRuntimeAdapter.ts`.
- **Encoder, nicht gestartet:** der Wortwolken-Encoder; sein Profil ist ab Werk aus, also keine Abweichung.
- **LLM-Server, llm-host:** `llama-server`, ein Slot, lauscht nur im privaten Netz, `--api-key`.

Darunter zwei Absätze: der Abgleich Punkt für Punkt mit ADR-0035 und dem Abnahmeprotokoll des Runbooks, und die auffälligste Lücke zur Ausgabegrenze. Keine Aufbaustufen.

**Herkunft.**

- Komponenten: `evidenz/1B/2026-11-12-aufbau.md`, Abschnitt Komponenten am Stand des Aufbaus, Code `a19ca70f`, ThinkPad P50. Der LLM-Server ist `llama-server` b10524 mit Qwen3-4B Q4_K_M und lauscht nur auf `192.168.150.20:8080`; ufw lässt nur `192.168.150.10` zu.
- Abgleich mit ADR-0035: gleiches Protokoll, Abschnitt Abgleich mit ADR-0035. Abweichend ist nur der Aufbau auf einem Rechner und die CPU-Zahl; einige Punkte sind im Aufbau nicht prüfbar, etwa die DNS-Auflösung, weil das Labor eine feste IP nutzt.
- Abnahmeprotokoll des Runbooks: abweichend Baseline-Commit statt Tag, Token ohne Passwortmanager, Summary eingeschaltet.
- Lücke Ausgabegrenze: ADR-0035 Z. 184 nennt für `--n-predict` „Richtung 256“, der ausgelieferte `entrypoint.sh` Z. 40 setzt 768. Die Antworten hatten 506–613 Tokens; mit 256 wären sie abgeschnitten (`evidenz/1B/2026-11-13-lauf.md`, Manifest, Commit `8e9d1317`). Gemessen wurde das Release-Verhalten mit 768.

**Warum das zählt.** Der Nachbau ist nur so viel wert wie sein Abgleich mit der Vorlage. Die Folie zeigt, dass jede Anforderung einzeln geprüft wurde und wo der Nachbau abweicht. Die Lücke bei der Ausgabegrenze ist ein Befund über das Release selbst: Dokumentation und ausgelieferter Code passen nicht zusammen.

**Was die Folie nicht behauptet.** „Erfüllt aus Code oder Konfiguration“ heißt im Protokoll: Der Code setzt die Anforderung um; im Labor ausgelöst ist sie nur, wenn die Prüfung das nennt. Ein Test von einem dritten Host im Labornetz fand nicht statt; vom Laptop aus wurde nur geprüft, dass Port 8080 gesperrt ist (Issue #22). Die Images sind selbst gebaut, ihre Digests sind nicht mit Produktion vergleichbar.

## Begriffe

- **ADR-0035:** Die Architekturentscheidung des Projekts für eine selbst betriebene LLM-Runtime (llama.cpp statt Ollama) auf einem zweiten privaten Host.
- **Runbook:** Eine Schritt-für-Schritt-Anleitung für Aufbau und Betrieb; hier das Second-Host-Runbook des Projekts mit einem Abnahmeprotokoll.
- **App-Adapter:** Der Teil der App, der den Prompt baut, die Runtime aufruft, die Antwort prüft und sonst die Ersatzzusammenfassung liefert.
- **Encoder:** Ein separater Dienst für Wortwolken und Labels; ab Werk aus.
- **LLM-Server (`llama-server`):** Das Programm aus llama.cpp, das das Modell lädt und per HTTP Anfragen beantwortet.
- **`--api-key`:** Startoption des LLM-Servers: Er verlangt einen Token bei jeder Anfrage.
- **Bearer-Token:** Ein geheimer Schlüssel im Kopf der HTTP-Anfrage, der den Absender ausweist.
- **`--n-predict`:** Höchstzahl der Tokens, die das Modell in einer Antwort erzeugen darf.
- **Token:** Ein Textstück, mit dem das Modell rechnet, oft ein Wortteil.
- **Digest:** Prüfsumme eines Container-Images; gleicher Digest heißt bitgleiches Image.
- **Baseline-Commit / Tag:** Ein Commit ist ein Codestand, ein Tag ein benannter Release-Stand. Gemessen wurde der Commit `a19ca70f`, kein Tag.

## Fragen

### Wo genau liegen App-Adapter, Encoder und LLM-Server?

Der Adapter läuft in der App auf dem app-host, Container `arsnova-v3-app`. Der Encoder ist nicht gestartet, ab Werk aus. Der LLM-Server läuft allein auf dem llm-host, Container `arsnova-open-weight-llm`, und lauscht nur auf der privaten Adresse.

### Was bedeutet die Lücke bei der Ausgabegrenze?

ADR-0035 empfiehlt etwa 256 Tokens, das Release setzt 768. Die echten Antworten hatten 506–613 Tokens; mit der ADR-Empfehlung wären sie abgeschnitten. Ich habe das Release-Verhalten gemessen und die Lücke als Befund festgehalten.

### Haben Sie geprüft, dass ein dritter Host die Runtime nicht erreicht?

Nur teilweise. Einen dritten Host im Labornetz gab es nicht; vom Laptop aus ist geprüft, dass Port 8080 gesperrt ist, und die Tests ohne und mit falschem Token liefen im llm-host selbst. Dass das Runbook keinen Befehl dafür nennt, ist als Issue #22 angelegt.

### Welche weiteren Lücken des Nachbaus haben Sie gefunden?

Image-Digests stehen nicht im Repo, Runbook §6 bricht den Produktions-Wrapper, ein Befehl für den Dritthost-Test fehlt, der App-Start hängt an der Redis-Bestätigung, und große Layer laufen beim Push in Timeouts (Aufbauprotokoll, Befunde 1–5; Issues #21, #22).

### Ist das noch das Release 1.3?

Die Architektur stammt aus Release 1.3, gemessen wurde aber der Code nach v1.4.0, auf Wunsch des Prüfers. Die Abweichungen zum Tag sind dokumentiert; die Übertragbarkeit ist eine Gültigkeitsgrenze.
